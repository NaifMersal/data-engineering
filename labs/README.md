# Modern Data Engineering: labs

Hands-on notebooks for the SDAIA Academy **Modern Data Engineering** bootcamp (Data Engineering track). Every lab builds a piece of one platform for **Qafila**, a fictional quick-commerce grocery company in Riyadh, Jeddah and Dammam: from raw sources to a governed, AI-ready lakehouse.

## Quick start

**Google Colab**
1. Open a notebook from the [course page](https://sdaiaacademy.github.io/data-engineering/), or directly: `https://colab.research.google.com/github/SDAIAAcademy/data-engineering/blob/main/labs/<notebook>.ipynb`.
2. Run the first cell. It clones this repository, installs `requirements-colab.txt` and generates the data. A CPU runtime is enough for every lab.

**Local (any laptop CPU)**
```bash
git clone https://github.com/SDAIAAcademy/data-engineering
cd data-engineering/labs
uv sync                        # creates .venv from pyproject.toml (uv.lock pins every version)
uv run python prepare_data.py  # generates data/raw (≈35 MB, a few seconds)
uv run jupyter lab
```
Run `00_setup_check.ipynb` once before Day 1: it builds the shared warehouse, downloads the Day 4 embedding model and smoke-tests DuckDB, Iceberg and dbt.

New to SQL window functions? Walk through `00_sql_windows.ipynb` before Day 1 (self-paced, about 60 minutes, no exercises). It builds `PARTITION BY`, ranking, `LAG`/`LEAD`, frames and `QUALIFY` up from tables small enough to check by eye, and ends with a customer's city history: the table Day 1's last session names SCD Type 2 and Lab 1.4 builds at scale.

**Spark** (`tools/spark.ipynb` and Lab 3.2) needs Java 17+. On Colab the notebook installs it. Locally, install a JDK (for example [Temurin 21](https://adoptium.net/)), set `JAVA_HOME`, then `uv sync --extra spark`. On native Windows, Spark also needs `winutils.exe` to write files, so Windows users should run the Spark notebooks on Colab (or in WSL).

Set `DE_QUICK=1` to shrink the heavier workloads. Useful on slow laptops and for checking that notebooks run.

## Tool walkthroughs

Each one starts with the job done by hand and watches it break, gives the tool's mental model, then builds its features one at a time on Qafila data, with 🤔 predictions and self-checks. They have no exercises: you practise in the lab that follows. Each ends with a summary: what the tool does and doesn't, where the course uses it, its managed services, a cheat sheet and checkpoint questions. Sections marked ➕ are for your own pace. The instructor copies, with the 🎓 notes and the class timings, are in `solutions/tools/`.

**DuckDB** (D1_1, [`tools/duckdb.ipynb`](tools/duckdb.ipynb)): one business question asked of the app database (SQLite) and of pandas, then of DuckDB, a fraction of the time and a file several times smaller. Then the engine itself: in-process, columnar, vectorized; connections and database files; CSV sniffing, globs with `union_by_name`, nested JSON, Parquet; tables vs. views; attaching SQLite; the one-writer lock, broken on purpose; DataFrames and relations in Python; friendly SQL; reading `EXPLAIN ANALYZE`. Lab 1.1 then points it at the real sources.

**dlt** (D1_3, [`tools/dlt.ipynb`](tools/dlt.ipynb)): a loader written by hand breaks in four ways (retries, refunds, a new field, the cursor), then dlt does the same job while you read the files and tables it produces. Write dispositions, an incremental cursor whose state survives deleting the pipeline folder, a late record that slips past the cursor and the lag that catches it, nested data, variant columns and schema contracts. Lab 1.3 then applies it to the real payments API and app database.

**Polars** (D2_1, [`tools/polars.ipynb`](tools/polars.ipynb)): a question answered by a Python loop over the courier feed, about 20 times slower than the same lazy query. Then DataFrames and types, expressions and their four contexts, `filter`, `with_columns` (time zones), `group_by`, joins (an anti join finds the orphan orders), `over`, lazy plans and pushdown, and one chain checked against SQL. Lab 2.1 then cleans the messy parts: timestamps, duplicates, customers.

**dbt** (D2_3, and §9 opens D2_4, [`tools/dbt.ipynb`](tools/dbt.ipynb)): three SQL files run by hand go wrong (run order, a stale report), then Finance's city revenue report built as a project from an empty folder, reading every piece of SQL dbt generates: sources, a view, `ref()` and the graph, view vs. table vs. incremental (broken on purpose), macros, tests. Then warn vs. error, an enforced contract, a unit test that catches what every data test misses, and where each check belongs. Step-by-step players replay each run. Lab 2.3 builds the Qafila project; Lab 2.4 adds its tests.

**Pandera** (D2_4, after `tools/dbt` §9, [`tools/pandera.ipynb`](tools/pandera.ipynb)): a day of payments with six problems, checked first with hand-written asserts (one failure per run, nulls slip through), then with a Pandera schema: types and nulls, built-in and custom checks, every failure at once with its row, a quarantine split, and the LazyFrame trap broken on purpose. It maps each rule to its dbt test and, at your own pace, runs a schema on the real payments feed. Lab 2.4 then validates the supplier price files.

**Iceberg** (D3_1, [`tools/iceberg.ipynb`](tools/iceberg.ipynb)): a folder of Parquet files hides a failed load and can't change one row. Then an Iceberg table, layer by layer: the catalog, one commit bottom-up (and a crash before the pointer swap), readers skipping files, a copy-on-write delete, time travel, two writers racing, a rename that rewrites nothing, DuckDB on the same table at any version. Boards replay each step from the table's own metadata files. Lab 3.1 then builds `qafila.orders`.

**Spark** (D3_2, [`tools/spark.ipynb`](tools/spark.ipynb)): do you need a cluster at all? Then the driver, executors and tasks, partitions, lazy plans, the shuffle, broadcast vs. sort-merge joins, skew and one file per task, each drawn from what Spark just returned. Runs on Colab (Java 17+). Lab 3.2 then measures pruning, broadcasts, salting and small files.

**Dagster** (D4_1, [`tools/dagster.ipynb`](tools/dagster.ipynb)): a nightly script breaks the usual ways (a re-run loads a day twice, a refund flows into the report, nobody knows what was built when), then the same pipeline as Dagster assets. Selecting part of the graph, the run history and stale assets, resources for dev and prod, a partitioned asset that doubles its rows on a re-run until it is made idempotent, a non-blocking and a blocking asset check, schedules, a sensor with a cursor, retries, and a small dbt project whose models and tests join the graph. A player replays each run from its event log. Lab 4.1 then orchestrates the real warehouse.

Every walkthrough also has a **read-only copy with all its outputs** in `tools/html/` (linked as "read" on the course page), for reading without running, or when Colab is slow.

## Data

`prepare_data.py` generates everything in `data/raw/`. It is synthetic and deterministic (fixed seed): August–September 2026, no real personal data, and it works offline.

| Source | File | Rows | Deliberate problems |
|---|---|---|---|
| App database (SQLite) | `qafila_oltp.sqlite` | 7,442 customers · 12 stores · 356 products · 45,766 orders · 172,545 order items | duplicate accounts, mixed mobile formats, soft deletes, orphan orders after erasure, negative quantities |
| Payments API (mock REST service in `de_utils.PaymentsAPI`) | `api/payments.jsonl` | 41,785 | pagination, rate limits, failed attempts, a field added on 15 September |
| Customer CDC feed (Debezium-style) | `cdc/customers_changes.jsonl` + `customers_snapshot_2026-09-01.csv` | 6,346 events | duplicates, out-of-order events |
| Courier delivery events | `events/delivery_events.jsonl` | 22,518 | late and duplicate events, three timestamp formats |
| Supplier price files | `suppliers/prices_2026-W36…W39.csv` | 640 | decimal commas, Arabic-Indic digits, a renamed column, bad costs |
| Product reviews (Arabic + English) | `reviews.csv` | 3,000 | free text for Day 4 |

`DATA_ISSUES.txt` lists every planted problem. Students find most of them in Lab 1.1, so open it afterwards.

`dbt_qafila/` is the dbt project for the course (staging → intermediate → marts, a quarantine model, tests and a model contract). Labs 2.3 to 4.4 and the capstone build it.

## Using an LLM (optional)

Only the text-to-SQL part of Lab 4.4 can use an LLM, and it falls back to a rule-based planner without one. To use any OpenAI-compatible endpoint (vLLM, Ollama, or a hosted provider), copy `.env.example` to `.env` and fill it in. The lab sends only the question and the metric and dimension descriptions, never data rows. Still, check your organisation's data policy before you use an external service.

## Capstone

`capstone/` holds the starter kit: `pipeline.py` (a working Dagster code location for option 1), an ODCS contract, the requirements, the rubric and a README template. See [capstone/README.md](capstone/README.md).

```bash
uv run python capstone/pipeline.py           # run the whole platform once (≈1–2 min)

```

## Editing the notebooks

Notebooks are generated from `_src/*.py` (percent format). Edit the source, then run:
```bash
uv run python _tools/py2nb.py                    # rebuild all (student + solutions)
uv run python _tools/py2nb.py D3_1_iceberg_lakehouse   # rebuild one
uv run python _tools/py2nb.py dbt                # one tool walkthrough: _src/tools/dbt.py → tools/ + solutions/tools/
```
A markdown cell headed `# %% [markdown] 🎓` is an instructor note: it goes into the solution notebook only.

The session tables of this README and of the course page come from one list in `_tools/sessions.py`: edit it, then `uv run python _tools/sessions.py`. The read-only copies in `tools/html/` are exported from the executed solution notebooks with `uv run python _tools/export_html.py` (execute a solution first if its outputs are stale; Spark needs Colab or WSL).
