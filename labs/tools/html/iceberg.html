Iceberg · open table formats, on a lightboard¶

Day 3, before Lab 3.1 · CPU only. A folder of Parquet files breaks as soon as a load dies halfway or one row must change. You watch it break, then build an Iceberg table commit by commit and replay what each commit wrote on disk.

The data: Qafila's payments feed; Lab 3.1 then builds the orders table. Same ideas, different table.

Rhythm: 🤔 predict → run → 🔍 read. After the code, a board (a step-by-step player) replays what just happened on disk, one piece at a time, the way you would draw it on a lightboard: click Next ▶ or ▶ Play. Except for the history board, everything on a board is read from the table's own metadata files.

Part A · Why Iceberg had to exist¶

0 · How we got here¶

Before any code, the story in six strokes. 🤔 Start with a question for the room: a database always knows what's in a table. Why doesn't a folder of files?

1 · A folder of Parquet files is not a table¶

The Day 1 way: one Parquet file per day in a folder, and readers glob the folder. A nightly job loads four more days and dies after writing two of them.

The problem is that in a folder, writing a file is publishing it, so readers see whatever the job managed to write, and nothing records what it was supposed to write.

Then finance asks us to mark one payment as refunded, and Parquet files are immutable: there's no UPDATE.

Readers that see half-finished loads, no safe updates, no safe concurrent writers, and no single place that says what the table contains. A table format fixes all of these the same way: a metadata layer that lists exactly which files make up the table at each version.

Part B · How it works, layer by layer¶

Iceberg splits "the table" into layers, and each layer answers one question:

Layer Answers How many
catalog where is the table now? one row per table: the path of the current metadata file
metadata file (*.metadata.json) what is the table, and what was it? one per commit: schema, partition spec, the list of snapshots, the earlier metadata files
manifest list (snap-*.avro) which manifests make up this snapshot? one per snapshot
manifest (*-m0.avro) which data files, and what's in them? file paths, row counts, min/max per column
data files (*.parquet) the rows never edited, only added or dropped

Two counting rules for the rest of the demo:

  • Every commit writes a new metadata file. Nothing is edited in place; the catalog pointer moves to the new file.
  • Only commits that change data create a snapshot. A snapshot is a version of the table's data. Changing the schema or the partitioning writes a metadata file, but no snapshot.

We build it in that order: the catalog first, then one commit from the bottom up.

2 · The catalog is one pointer¶

PyIceberg's SqlCatalog keeps the catalog in a SQLite file; the "object store" is a local folder. In production the catalog is a REST service (Polaris, Unity Catalog, Glue, Lakekeeper...) and the folder is S3 or ADLS.

The table gets a partition spec: the rule for grouping rows into files, written as source column + transform. Ours is day(created_at), so every day's payments land in their own files. On write, Iceberg applies the transform to each row (we never add a created_day column ourselves); on read, it turns a filter on created_at into a filter on the partition, which is how section 4 skips files. The spec lives in the metadata file, not in folder names, so it can change later without rewriting data (Lab 3.1 does that). Other transforms: month, hour, bucket(N), truncate(W), identity.

Why two metadata files? Because that cell made two commits:

Notice the field ids (1, 2, 3...). Iceberg tracks columns by id, not by name. Section 8 uses that.

This file is also the table's history. There's no separate log: each commit copies the list of snapshots and the list of earlier metadata files from the previous metadata file, then adds its own entry. So far: three commits (00000, 00001, 00002), one snapshot, because only the append changed data. The catalog only needs the newest file; everything older is reachable from it. (Delta Lake keeps the same information as a numbered log, _delta_log/000…0.json, 000…1.json, …, and Hudi as a "timeline". Same idea, different file layout.)

A snapshot records which files make up the table, not which rows changed. Its summary says what kind of change and how much; to see exactly what changed, compare two snapshots' manifests. That's what every board does.

What if the load dies before the pointer swap?¶

Back to section 1's failure: the nightly load of days 5 to 8 dies. This writer gets further than the folder job did: it writes all the Parquet files, then dies just before committing. A PyIceberg transaction lets us stop right there: append writes the data files immediately, and only commit_transaction() writes the metadata and swaps the pointer.

PyIceberg removed the whole file for 3 August and wrote a new one without that row: copy-on-write. Reads stay fast, but writes cost a whole file per changed row. Spark and Flink can also write merge-on-read: keep the data file and add a small delete file (a deletion vector in Iceberg v3) that readers merge in. Cheap writes, slower reads until compaction.

The snapshot summary above says what kind of change and how much. Which row went is not recorded anywhere: you find it by comparing the removed file with the one that replaced it.

6 · Time travel¶

The old file wasn't deleted from disk. It's just no longer in the current snapshot. Time travel uses the history from section 3: pick an older snapshot from the current metadata file's list and follow its manifest list down.

B wrote its Parquet file without any lock. At commit time it asked the catalog to swap the pointer from the version it read. The pointer had moved, so the swap failed (the "Commit failed … retrying" line). B re-read the new metadata, checked that A's append doesn't conflict with its own, and committed on top. Data files are never shared, so only the pointer swap needs to be serialized.

When the changes do conflict¶

Appends never conflict: each one adds its own files and removes nothing. Deletes and overwrites are different. They remove files, and they were planned against the snapshot the writer read. So on retry the writer checks the commits it missed: did any of them add or remove a file my filter could match? If so, it fails instead of committing a change it planned on data that has since changed.

Three races, each starting from the snapshot both writers read. 🤔 Predict each outcome before running:

Writer A Writer B
1 deletes payment X from 3 August deletes payment Y, also from 3 August
2 deletes a payment from 3 August deletes a payment from 4 August, and the filter names the day
3 deletes a payment from 3 August deletes a payment from 4 August, filter on payment_id only

from pyiceberg.exceptions import ValidationException

def race(a, b):
    """A and B load the same snapshot; A commits, then B tries."""
    writer_a, writer_b = catalog.load_table("qafila.payments"), catalog.load_table("qafila.payments")
    a(writer_a)
    try:
        b(writer_b)
        return "both committed"
    except ValidationException:
        return "B failed: conflict"

def on_day(d):
    return f"created_at >= '2026-08-{d:02d}T00:00:00' and created_at < '2026-08-{d + 1:02d}T00:00:00'"

  1. Conflict. Both writers rewrite the one 3 August file. A's new file still holds Y; B's new file would still hold X. Had B committed anyway, 3 August would be in the table twice. B stops instead, and nothing it wrote is visible: its commit never landed.
  2. No conflict. The filters name the day, so Iceberg proves from the partition values alone that A's new 3 August file can't hold B's 4 August row.

The check sees only metadata, so when in doubt it fails. Put the partition column in the filter (race 2) and the false conflict goes away; Spark and Delta give the same advice for MERGE.

A failed writer recovers the way any optimistic system does: reload the table and run the job again. (On Day 4 the orchestrator does that retry for you.)

Four open table formats. The same idea, a metadata layer over Parquet files; they differ in where that metadata lives.

Format From Metadata lives in Known for
Apache Iceberg Netflix → Apache JSON + Avro files, and a catalog the broadest engine support; the usual "many engines, one copy" choice
Delta Lake Databricks → Linux Foundation a numbered log, _delta_log/*.json + checkpoints Databricks' default; UniForm exposes Delta tables as Iceberg
Apache Hudi Uber → Apache a timeline of files record-level upserts and incremental pulls
DuckLake DuckDB Labs a SQL database (PostgreSQL, SQLite, DuckDB) Parquet data with the catalog and metadata in SQL: simple, fast commits

Which one? Follow your engines and your catalog. Iceberg v3 (2025) shares deletion vectors with Delta and adds a VARIANT type for semi-structured JSON: the formats are converging.

The catalog is the control plane. Every engine must agree on one thing: which metadata file is current. The Iceberg REST catalog spec lets any engine talk to any catalog over HTTP, and catalogs now also hand out short-lived storage credentials and enforce access control, so governance moves there (Day 4). Open source: Apache Polaris, Unity Catalog OSS, Lakekeeper, Nessie, Apache Gravitino. In the cloud: AWS Glue / S3 Tables, Databricks Unity Catalog, Snowflake Open Catalog, BigLake.
