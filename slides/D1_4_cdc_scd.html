Log-based CDC (e.g. Debezium on PostgreSQL logical replication or the MySQL binlog) emits every insert, update and delete, in commit order, without querying the tables.
Common path: DB log → Debezium → Kafka → sink (lakehouse table or warehouse). Managed: Fivetran, AWS DMS, Datastream, Confluent connectors.

Applying changes

Dedupe, keep the latest per key, then MERGE

WITH changes AS (
  SELECT DISTINCT ON (source.lsn) *              -- 1 · drop redelivered duplicates
  FROM read_json_auto('data/raw/cdc/customers_changes.jsonl')
), latest AS (
  SELECT coalesce(after.customer_id, before.customer_id) AS customer_id, op, after
  FROM changes
  QUALIFY row_number() OVER (PARTITION BY coalesce(after.customer_id, before.customer_id)
                             ORDER BY source.lsn DESC) = 1   -- 2 · last change per key wins
)
MERGE INTO customers AS t
USING latest AS s ON t.customer_id = s.customer_id
WHEN MATCHED AND s.op = 'd' THEN DELETE                       -- 3 · hard delete
WHEN MATCHED THEN UPDATE SET city = s.after.city, district = s.after.district,
                             mobile = s.after.mobile, updated_at = s.after.updated_at
WHEN NOT MATCHED AND s.op <> 'd' THEN INSERT (customer_id, city, district, mobile, updated_at)
  VALUES (s.customer_id, s.after.city, s.after.district, s.after.mobile, s.after.updated_at);
MERGE is standard SQL (DuckDB ≥ 1.4, Spark/Delta, Iceberg, Snowflake, BigQuery). Ordering by lsn, not by arrival, is what makes out-of-order delivery harmless.
The INSERT branch is simplified on the slide; in the lab the column list is explicit. DISTINCT ON keeps one row per lsn: a redelivered event is identical, so it doesn't matter which copy survives.
Deletes

Hard, soft, and tombstones

Hard delete

Row disappears from the source. Invisible to cursors; CDC emits op = d. Required for erasure requests under PDPL.

Soft delete

Source sets is_deleted = 1 (an update). Easy to replicate, but every consumer must filter it.

Tombstone

In Kafka, a message with a key and a null value: "forget this key" for compacted topics.

Decide explicitly how each layer represents deletes. A common choice: bronze keeps every event; silver applies hard deletes; marts exclude soft-deleted rows. Personal data must really disappear from every layer and every snapshot (Day 4).

Checkpoint

A batch of CDC events has three changes to customer 42, delivered out of order. You MERGE them without the dedupe step. What goes wrong?

Nothing: MERGE applies the changes in the order they arrive
Several source rows match one target row: the MERGE fails, or one change wins at random
The newest change is applied twice
B. A MERGE needs at most one source row per key. Keep the latest change per key, ordered by the log position (lsn), not by arrival: then out-of-order delivery is harmless.
