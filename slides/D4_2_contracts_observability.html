Data observability

Five things to watch on every important table

Freshness

When did it last change? Is that later than promised?

Volume

Did today's load bring roughly the expected number of rows?

Schema

Columns added, removed, renamed, retyped.

Distribution

Null rates, value ranges, category mix drifting.

Lineage

What feeds this table, and who reads it? Who must be told?

+ Cost

FinOps: which models and queries burn the budget? Track it like any other metric.

Tests check what you expect. Monitors catch what you didn't think to test. You need both. Tools: Elementary, Soda, Monte Carlo, Datadog, plus orchestrator freshness checks and OpenLineage for cross-tool lineage.

Model seasonality (weekday, Ramadan, month-end), keep a calendar of planned events, and route alerts to the table's owner.
Data contracts

An agreement between producer and consumers, in code

  • Schema: fields, types, keys, required, unique.
  • Semantics: what each field means, units, what's excluded.
  • Quality rules: row counts, valid values, custom SQL.
  • Service levels: latency, frequency, retention, support hours.
  • People: owner, consumers, support channel; classification of sensitive fields.
Open Data Contract Standard (ODCS, Bitol project, Linux Foundation AI & Data): one vendor-neutral YAML format. v3.1 is the current release; v3.2 is in development.
Contracts sit at team boundaries: a provider's feed, a domain's published tables, a mart other teams build on. Not every staging model needs one.
ODCS in practice

The payments feed contract (excerpt)

apiVersion: v3.1.0
kind: DataContract
team:
  - {username: payments-provider-integration, role: owner}
schema:
  - name: payments
    quality:
      - type: sql
        query: SELECT count(*) FROM {object} WHERE amount <= 0
        mustBe: 0
    properties:
      - name: status
        required: true
        quality:
          - metric: invalidValues
            arguments: {validValues: [captured, failed, refunded]}
            mustBe: 0
slaProperties:
  - {property: latency, value: 1, unit: d}
Lab 4.2: 26 of 27 checks pass. The contract finds 16 payments with amount ≤ 0: now it's a breach with an owner and a support channel, not "weird data".
The same file generates dbt tests (Lab 4.2 ✱) and orchestrator checks (capstone/pipeline.py). Tooling: the datacontract CLI.
Change management

Breaking or not?

Change (from the consumer's side)Breaking?Why
Column removed or renamed (amount → amount_sar)✗ yesqueries fail
Type changed (card_last4 string → integer)✗ yesleading zeros lost, joins and casts break
New allowed value (status = 'chargeback')✗ yesconsumers' CASE logic silently mishandles it
Required field becomes optional✗ yesunexpected nulls
New column; optional field becomes required; fewer allowed values✓ noexisting queries keep working
Breaking → new major version, published next to the old one with a migration window. Run the contract diff in the producer's CI; use lineage to list who must migrate (Lab 4.2: 4 models and 7 tests read raw.payments).
Checkpoint

The payment provider adds 'chargeback' as a new status value. Breaking for consumers?

No: no column was added or removed
Yes: code that handles every known status will mishandle the new one, often silently
Only if the column type changes
B. Think of revenue logic like CASE WHEN status = 'refunded' THEN 0 ELSE amount END: chargebacks would count as revenue. Widening an enum is a breaking change.
