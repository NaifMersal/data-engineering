Store

How analytical data sits on disk

The map for the whole course, with today's stage marked. Parquet is the store under almost everything that follows: DuckDB reads it, Iceberg (Day 3) is a table made of Parquet files, Spark writes it. This session is about why the file layout decides how much a query has to read.
Layout matters

Row storage vs. column storage

Row-oriented: each record stored together

5001 · RUH-01 · 84.5 · delivered5002 · JED-02 · 31.0 · cancelled5003 · RUH-01 · 12.0 · delivered

Column-oriented: each column stored together

5001 · 5002 · 5003RUH-01 · JED-02 · RUH-0184.5 · 31.0 · 12.0delivered · cancelled · delivered
Read only what you need: SUM(amount) touches one column out of thirty.
Compresses well: similar values sit next to each other (RUH-01, RUH-01, …).
Vectorized: CPUs process a column chunk in tight loops (SIMD).
Trade-off: single-row inserts and updates are expensive, so batch your writes.

Inside a Parquet file

Row groups, column chunks, pages and a footer

  • Row group: a horizontal slice (DuckDB: 122,880 rows; Spark: ~128 MB). The unit of parallelism and skipping.
  • Column chunk: one column inside a row group, split into pages.
  • Footer: read first. It holds the schema and the statistics engines use to skip data.
  • Encodings: dictionary (repeated strings), run-length, delta (sorted ints, timestamps).
  • Compression on top: Snappy (fast), ZSTD (smaller; a good default today).
Pushdown

The fastest data is the data you never read

-- Projection pushdown: read 2 of 9 columns
-- Predicate pushdown: skip row groups whose
--   max(created_at) < '2026-09-23'
EXPLAIN ANALYZE
SELECT store_id, sum(amount)
FROM 'orders.parquet'
WHERE created_at >= '2026-09-23'
GROUP BY store_id;

-- Inspect what the engine can use to skip
SELECT row_group_id, path_in_schema,
       stats_min, stats_max, compression
FROM parquet_metadata('orders.parquet');
Projection pushdown: only the referenced columns are decoded. SELECT * defeats it.
Predicate pushdown: row groups whose min/max cannot match are skipped entirely.
Sort to skip: statistics only help if values are clustered. Sorting by created_at before writing makes date filters skip almost everything.
Partitioning

Directories as a coarse index

orders/
  order_date=2026-09-22/part-0.parquet
  order_date=2026-09-23/part-0.parquet
  order_date=2026-09-24/part-0.parquet
  ...
con.sql("""
  COPY (SELECT *, created_at::DATE AS order_date
        FROM orders)
  TO 'lake/orders' (FORMAT parquet,
                    PARTITION_BY (order_date))
""")
# a filter on order_date opens one folder
con.sql("""SELECT count(*) FROM read_parquet(
  'lake/orders/*/*.parquet', hive_partitioning=true)
  WHERE order_date = '2026-09-23'""")
Good partition keys are low-cardinality and match how data is filtered and loaded: date, country, tenant.
Over-partitioning (by customer, by hour for small tables) creates thousands of tiny files: listing and opening them costs more than reading the data.
The small-files problem

Many tiny files are slow, expensive and fragile

1 × 1 GB file
fast
100 × 10 MB files
ok
10,000 × 100 KB files
slow

Same data, illustrative relative read time: each file costs a request, a footer read and planning work.

  • Typical targets: files of 128 MB – 1 GB, row groups of ~128 MB.
  • Streaming and frequent micro-batches create small files by design (Day 3).
  • Fix with compaction: periodically rewrite small files into big ones. Table formats make that safe for concurrent readers.
Checkpoint

A 20 GB Parquet table is filtered by created_at in almost every query, yet each query reads all 20 GB. Most likely cause?

Parquet can't filter on timestamps
Rows were written in random order, so every row group's min/max covers the whole date range
The files are compressed with ZSTD instead of Snappy
B. Statistics only let the engine skip row groups when values are clustered. Sort (or partition) by the filter column when writing.
