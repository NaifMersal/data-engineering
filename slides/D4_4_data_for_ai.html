The serve stage now has a new consumer: a model that answers questions in Arabic and English. It needs the same things a dashboard needs (one definition per metric, clean gold tables) plus search by meaning. The platform executes; the model only chooses.

The risk: a model writing SQL on raw tables gives confident, inconsistent numbers ("revenue" with or without fees? refunds?). The fix is the same as for humans: governed definitions, good descriptions, access control.
Semantic layer

Metrics defined once, compiled to SQL everywhere

from: marts.fct_orders AS o
joins: [marts.dim_stores AS s USING (store_id)]
dimensions:
  city:  {expr: s.city}
  month: {expr: "date_trunc('month', o.order_date)::DATE"}
metrics:
  revenue_sar:
    expr: "round(sum(o.items_amount)
           FILTER (WHERE o.status = 'delivered'), 2)"
    description: Revenue, sales from delivered orders,
      SAR, excl. delivery fees. المبيعات والإيرادات
run({"metrics": ["revenue_sar"],
     "dimensions": ["city"],
     "filters": [["month", "=", "2026-09-01"]]})
# Riyadh 1,748,564.50 · Jeddah 1,062,633.91 …
Same numbers as the dashboard mart, by construction. Tools: dbt Semantic Layer (MetricFlow), Cube, LookML, Snowflake semantic views.

        "(product_id BIGINT, vec FLOAT[256])")
con.execute("""
  SELECT name_en, array_cosine_similarity(
           vec, ?::FLOAT[256]) AS score
  FROM product_vectors JOIN raw.products USING (product_id)
