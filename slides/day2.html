DuckDB & Polars

Clean the records, understand the plan, and save a reusable Silver layer.

01
Explain the problem before naming the tools. DuckDB and Polars both execute transformations locally in our labs. SQL and DataFrames are interfaces. Neither interface makes a result correct by itself.
The problem · Inconsistent source records

Bronze keeps the source. Silver makes it consistent.

Bronze value or problemSilver resultReason

The same event_id arrives twiceOne chosen copy per eventAvoid counting one event twice

Why this matters: Preserving the original records lets us correct and rerun a cleaning rule.
Silver rules express technical and business assumptions, so document them. The boundary between Silver and Gold can vary by team. Here Silver standardizes records. Gold defines analytical structures and metrics. Keep source lineage and rejected values rather than silently discarding them.
The value and philosophy

DuckDB and Polars separate rules from execution

You describe the result. The engine plans the work.

ToolWhat you writeWhat it provides
DuckDBSQL over tables or filesLocal joins and aggregations without a database server
PolarsPython expressions over columnsA DataFrame pipeline with lazy planning

Both help us turn Bronze records into reusable Silver data on a laptop. We still define the cleaning rules.

Keep this introduction brief. The problem is inconsistent input and repeated transformation work. DuckDB runs inside the application process. Polars lets us express column operations in Python. With a lazy scan it can plan several operations together. Neither tool chooses the business meaning of a timestamp, duplicate, or revenue amount.
How it works · The execution engine

Less data to read means less work

Engine ideaIn this queryWhy it helps
Columnar readingRead store_id and statusOther columns need no scan for this calculation
Filter pushdownApply delivered status near the scanFewer rows enter later operators
Batch executionProcess many values per operationReduce work spent dispatching each row
Parallel executionSplit work across CPU coresIndependent chunks run at the same time

The optimizer chooses a plan. Available memory, file format, and the query affect the benefit.

Avoid promising a particular batch size or storage layout across all products. DuckDB uses vectorized execution. Polars exposes column expressions and parallel processing. These tools can exchange Arrow data, but conversions are not always free. Source: DuckDB internals.
How to use it · SQL or Python

A processing engine runs the transformation

DuckDB

A database engine we query with SQL.

SELECT store_id, COUNT(*) AS orders
FROM raw.orders
WHERE status = 'delivered'
GROUP BY store_id;

Polars

A DataFrame engine we use from Python.

result = (orders
    .filter(pl.col("status") == "delivered")
    .group_by("store_id").len()
    .collect())
Assume import polars as pl and an orders LazyFrame in the Python example. SQL COUNT(*) and Polars group_by.len count rows, including rows whose non-key columns are null. The output column names differ here. In the lab we also align names, sorting, and rounding before comparing results.
Step 1 · Inspect the work

A query plan explains the engine’s work

EXPLAIN ANALYZE
SELECT store_id, COUNT(*)
FROM raw.orders
WHERE status = 'delivered'
GROUP BY store_id;
  1. Scan: read the input columns.
  2. Filter: retain qualifying rows.
  3. Aggregate: count rows for each store.
  4. EXPLAIN shows the plan. EXPLAIN ANALYZE also runs it and reports measurements.
Read a physical plan from the scan toward the final result. A filter may appear inside the scan rather than as its own box. Timings and operator names depend on the engine and version. Source: DuckDB EXPLAIN ANALYZE.
Step 2 · Plan before execution

Lazy execution keeps the whole plan visible

query = (pl.scan_parquet("orders.parquet")
    .filter(pl.col("status") == "delivered")
    .select("order_id", "store_id"))

print(query.explain())   # inspect the plan
result = query.collect() # execute and return a DataFrame
Why this matters: Starting with a scan lets Polars consider the filter and selected columns before reading the file.
A LazyFrame describes work to do. collect executes it and returns results. Calling lazy on an already loaded DataFrame can optimize later transformations, but cannot undo the earlier file read. Streaming support depends on the query, and a local engine still has resource limits. Source: Polars lazy usage.
Step 3 · Standardize time

One event can have several timestamp spellings

Source textMeaning in UTC
2026-09-23T01:30:00+03:0022 Sep 2026, 22:30 UTC
2026-09-22T22:30:00Z22 Sep 2026, 22:30 UTC
Epoch milliseconds for the same instant22 Sep 2026, 22:30 UTC
  1. Identify the format before parsing.
  2. Convert every valid value to one timezone-aware UTC type.
  3. Count parsing failures and keep the raw text for investigation.
Epoch milliseconds count elapsed milliseconds from 1970-01-01 UTC. They are not formatted calendar dates. Do not compare timestamp text as though every source uses the same representation. In the lab ingest time and event time are separate columns.
Step 3 · The code

Parsing tries each supported representation

et = pl.col("event_time")
parsed = bronze.with_columns(
    pl.coalesce(
        pl.from_epoch(et.cast(pl.Int64, strict=False),
                      time_unit="ms").dt.replace_time_zone("UTC"),
        et.str.to_datetime(format="%+", time_zone="UTC", strict=False)
    ).alias("event_at_utc")
)
failures = parsed.filter(pl.col("event_at_utc").is_null())
Why this matters: strict=False allows another parser to try. The failure check prevents invalid text from disappearing unnoticed.
coalesce takes the first non-null parsed value. This teaching example supports epoch milliseconds and offset-bearing ISO text. It assumes numeric timestamps are milliseconds. Unexpected units need their own validation. replace_time_zone labels the naive epoch result as UTC. It is not a conversion of an existing local timestamp. Source: Polars datetime parsing.

The same business calculation in both engines

  ROUND(SUM(i.quantity * i.unit_price
            - i.discount), 2) AS revenue
FROM raw.orders o

WHERE o.status = 'delivered'
GROUP BY o.store_id

Session 2

Dimensional modeling

Decide what one row means before deciding how to calculate sales.

02
Use the example order lines throughout this session. Work through grain and fan-out slowly. The SCD2 and alternative-model slides offer context. Lab 2.2 builds Type 1 dimensions, not a historical customer dimension.
The problem and value · Shared sales definitions

Clean records still need a sales definition

“How much did we sell?” leaves several decisions open.

  • Do cancelled orders count?
  • Does sales include delivery fees?
  • Does “by city” mean customer city or store city?
  • If a customer moves, should past sales move too?
Why this matters: A model makes these choices explicit so analysts can reproduce the same answer.
For the worked example, product revenue means delivered line net amounts. Delivery fees remain a separate measure. Use store city, as in the lab business questions. The same model may support multiple metrics, but each needs a definition.
The philosophy

Dimensional modeling gives each row a clear meaning

Organize data around the business process people want to analyze.

  • Grain: state exactly what one row represents.
  • Facts: store measurements at that grain.
  • Dimensions: provide the context used to filter and group those measurements.

For Qafila: an order line holds quantity and net amount. Product and store dimensions explain what sold and where.

Dimensional modeling is a design approach. It does not require a particular software tool. Establish the process and grain before choosing measures. The star schema on the next slide shows how the design works. Then trace the actual source rows into it.
How it works

The star schema connects facts to context

  • Date: weekday, month, weekend.
  • Product: name, category, brand.
  • Store: store name and city.
  • Customer: analytical attributes such as city.

Each fact key must match exactly one dimension row.

Use the existing diagram to trace one line through date, product, store, and customer. In this lesson the dimension keys are unique. An SCD2 dimension contains multiple versions per business key, so facts must identify a particular version. The customer analytical dimension omits direct identifiers such as mobile and national ID.

Three fact types

Fact types describe different kinds of rows

Fact typeOne row representsWhat happens over time
TransactionOne sale, payment, or refund eventNew events add rows
Periodic snapshotOne product in one store on one dateEach reporting period adds observations
Accumulating snapshotOne order moving through fulfillmentThe row gains milestone timestamps
Do not infer additivity solely from fact-table type. Transaction amounts may be additive across disjoint events. Snapshot balances are often semi-additive. Accumulating facts can contain counts, durations, and amounts with different valid aggregations.

Using the star for another question

The date dimension supports daily comparisons

WITH daily AS (
  SELECT d.date_day, d.is_weekend, s.city,
         SUM(f.net_amount) AS revenue
  FROM star.fct_order_items f
  JOIN star.dim_date d USING (date_key)
  JOIN star.dim_store s USING (store_key)
  WHERE f.order_status = 'delivered'
  GROUP BY d.date_day, d.is_weekend, s.city
)
SELECT city, is_weekend, AVG(revenue) AS avg_daily_revenue
FROM daily GROUP BY city, is_weekend;
Why this matters: First total each day. Then average those daily totals, so days with more order lines do not get extra weight.
The lab defines Friday and Saturday as the weekend and flags September 23 for its National Day comparison. The query averages observed sales days. If a city has zero-sales days, build a complete calendar-by-city set and fill those daily totals with zero before averaging. Lab dim_store city is store city.

Session 3

dbt

Turn the SQL model into a repeatable build with explicit dependencies.

03
The model design from Session 2 remains our responsibility. dbt provides a way to organize, render, execute, document, and test transformation code against a connected engine. Avoid treating it as a new database.
The problem and value · Dependent SQL files

Several SQL files create a dependency problem

  • The order-line fact needs cleaned orders and items.
  • The order fact needs line totals and payment totals.
  • The daily sales mart needs the order fact.
  • If a source rule changes, downstream results may need rebuilding.
Why this matters: Someone must know what runs first and what needs rebuilding. dbt records those relationships in the project.
Ask what happens if daily sales runs before the order fact has refreshed. The SQL could succeed while reading stale results. The purpose of dependency tracking is to execute related transformations in the intended order.
The philosophy

dbt treats transformations as a project

Each model defines a result and declares what it depends on.

  • Keep transformation logic in versioned files.
  • Reference upstream models so dbt can track dependencies.
  • Keep tests and documentation alongside the models.

dbt manages the build. DuckDB executes the SQL in our lab.

The previous slide establishes the value: repeatable execution of dependent SQL. Here explain the philosophy before syntax. Models express the desired result, and references make dependencies explicit. The team still owns metric definitions and model grain. The lab loads source data before dbt runs.
How it works

A dbt build follows the dependency graph

  1. Read the project: models, source declarations, and configuration.
  2. Resolve dependencies: identify which upstream models each result needs.
  3. Render and execute: turn templates into SQL and submit work in dependency order.
  4. Check the results: run selected tests as their inputs become available.

Qafila example: staging orders feeds the order fact, which feeds daily city sales.

This is a conceptual build sequence. dbt can execute independent branches concurrently. Models and tests run according to graph dependencies, rather than all tests waiting until every model finishes. Materialization controls whether the executed SQL creates a view, rebuilds a table, or updates selected rows. Explain the graph before showing source() and ref().
How to use it · Make one model

A dbt model starts as a SELECT in a file

SELECT order_id, customer_id, status,
       created_at::TIMESTAMP AS created_at_utc
FROM {{ source('raw', 'orders') }}
  • You write: the transformation query.
  • dbt renders: source references and templates.
  • dbt executes: SQL that creates or updates a relation.
  • DuckDB runs: the actual query over data.
The source must be declared in YAML and the profile must point to the warehouse. This is an excerpt rather than the complete stg_orders model required by Lab 2.3. Models can have other forms, but the lab uses SQL models. dbt is not the ingestion mechanism in these exercises.

Step 5 · The code

A look-back window reprocesses recent changes

{{ config(materialized='incremental',
          unique_key='order_line_id',
          incremental_strategy='delete+insert') }}

WITH orders AS (
  SELECT * FROM {{ ref('stg_orders') }}
  {% if is_incremental() %}
  WHERE updated_at_utc > (
    SELECT MAX(order_updated_at_utc) - INTERVAL 3 DAY FROM {{ this }}
  )
  {% endif %}
)
-- The remaining SELECT joins these orders to their lines.
Why this matters: Reprocessing the overlap is safe when candidate keys are unique and matching rows replace the old rows.
is_incremental is true for an existing target table configured incremental when full-refresh is absent. this resolves to the target relation. The three-day overlap is the lab policy, not a guarantee against every late change. If an existing target is empty, MAX is NULL and this filter needs an explicit default or a rebuild. Source: dbt incremental configuration.

Session 4

Testing & data quality

Turn our assumptions into checks, then decide what happens when they fail.

04
Connect each check to a failure already seen today: duplicate event, missing customer, fee fan-out, parse failure, or changing column type. Quality work starts with a concrete expectation.
The problem and value · Silent data errors

A successful build can still contain bad data

ProblemBuild may still succeedUseful expectation
Duplicate order linesA table can contain repeated keysEach order_line_id is unique
Missing customer referenceA LEFT JOIN can retain an unmatched rowEvery mart customer ID matches a dimension
Fee fan-outSUM returns a plausible larger numberTotals reconcile at the proper grain
Invalid supplier costZero is still a numeric valueCost must be greater than zero
An engine validates syntax and types, but usually cannot infer the business meaning of a metric. Tests should explain why a result is wrong and what action follows. Passing structural checks alone does not establish that a real-world amount is accurate.
The philosophy and mechanics

Quality rules turn assumptions into evidence

State an expectation, check it, and decide what a failure means.

WhereTool and mechanismUseful result
Built warehouse datadbt data tests query for violationsFailing keys or rows to investigate
Transformation logicdbt unit tests compare fixed inputs and outputsEvidence that a rule handles a chosen case
Incoming DataFramesPandera checks a declared schema and value rulesA validation result with failure details

A useful check has an agreed response and someone responsible for follow-up.

Explain the mechanism before the code examples. An expectation must reflect the business meaning, such as one row per order line. An empty violation result only shows that this particular check found no problem. Checks cover chosen assumptions and do not prove every aspect of correctness. Contracts protect the published model shape, while value rules inspect data.
How to use it · Express an expectation

A data test asks for the failing rows

SELECT order_line_id, COUNT(*) AS copies
FROM marts.fct_order_items
GROUP BY order_line_id
HAVING COUNT(*) > 1;

How to read it

  • Zero rows: no violation found.
  • One or more rows: investigate those keys.
  • A query error: the check did not complete.
A data test runs against actual built data. dbt evaluates failure counts according to the test configuration, including any thresholds. Here use the default zero-failures expectation. A test-query error is distinct from an assertion that finds bad data. Source: dbt data tests.

Why Pandera? · Before loading a supplier file

Supplier files need checks at the DataFrame boundary

A file can parse successfully and still contain an invalid cost or an unknown SKU.

  1. Declare the expected data: column types and allowed values.
  2. Validate the parsed DataFrame: Pandera checks it against those rules.
  3. Route the result: keep accepted rows and record rejected rows with reasons.

The same schema applies to each delivery. Our pipeline code handles loading and quarantine.

Keep the problem and value brief. Pandera makes expectations executable at the Python DataFrame boundary. It validates data and reports failures. Step 6 · Validate incoming data

Pandera validates a DataFrame against explicit rules

import pandera.polars as pa

class SupplierPrice(pa.DataFrameModel):
    supplier_id: str = pa.Field(str_startswith="SUP-")
    sku: str = pa.Field(isin=known_skus)
    unit_cost_sar: float = pa.Field(gt=0)
    currency: str = pa.Field(isin=["SAR"])

try:
    SupplierPrice.validate(prices, lazy=True)
except pa.errors.SchemaErrors as exc:
    failures = exc.failure_cases
Why this matters: lazy=True collects multiple failures into one validation result.
Parse localized numeric text first so the schema checks canonical numbers. Validation reports failures but does not automatically write a quarantine table or load the remaining rows. These require explicit routing logic. Pandera lazy validation means collect failures, unlike the lazy execution plan in Polars. Source: Pandera Polars validation.
